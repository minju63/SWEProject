# FR-MY-001 프로필 보호 · 2026-11-19

사용자가 선택한 보호 범위는 **DB 관리자가 민감정보 원문을 읽을 수 없도록 하는 것**이다. 앱 서버 관리자까지 차단하는 종단간 암호화는 아니다.

혼인 상태(`marital_status`), 주거급여(`housing_benefit_status`), 특화대상(`special_targets`)을 AES-256-GCM으로 암호화하여 기존 비공개 Storage `user-workspaces/<user_id>.json`의 `sensitiveProfile`에 저장한다. 기존 `user_profile`의 세 컬럼은 NULL로 유지한다. 새 테이블이나 SQL 설치는 필요 없다. 검증된 로그인 사용자의 ID로만 복호화하며, 다른 사용자의 암호문으로 바꾸면 인증 검증에 실패한다. 조건 비교에는 복호화한 본인 값을 사용한다.

## 서버 실행 및 키 보관

암호화 키는 DB와 분리된 `backend/.local/profile-encryption-key.json`에 있다. Git에 포함하지 않는다. 서버 계정만 이 파일에 접근하도록 운영체제 권한을 제한하고, DB 백업과 분리된 비밀 저장소에 백업해야 한다. 서버를 옮길 때 동일한 키를 안전하게 이전해야 한다. 키를 잃으면 기존 암호문을 복구할 수 없다. 런타임은 키가 없거나 암호문이 변조되면 503을 반환하며 새 키를 자동 생성하지 않는다.

기존 서버와 마찬가지로 한 프로세스에서 실행하고 `.local`을 영구 보존한다. 여러 서버의 동시 쓰기를 지원하는 분산 잠금은 이번 범위가 아니다. 앱 서버에 키와 서비스 권한이 있으므로 서버 관리자에 대한 원문 비공개는 보장하지 않는다. 과거 DB 백업에 남은 원문은 이번 이전으로 삭제되지 않으며 별도 보존 정책이 필요하다.

## 이전 및 검증

backend 폴더에서 `node scripts/auth/protect-profile-data.js`는 읽기 전용 사전 점검이다. `--apply`를 붙이면 실제 서비스 프로젝트와 비공개 버킷을 확인하고 기존 민감정보를 이전한다. 원문이나 키를 출력하지 않는다. 먼저 암호문을 보존하고 SQL 컬럼을 비우므로 SQL 저장 실패 시 재시도할 수 있다. 두 저장소는 하나의 DB 트랜잭션이 아니며 실패 시 요청이 오류로 반환된다.

실제 반영 결과: 프로필 2건 중 1건 이전, 민감 원문 잔여 0건. 본인 조회값 일치, 다른 프로필 필드 및 기존 신청 기록 보존을 대조했다.

닉네임만 필수이고 나머지 선택 항목은 지울 수 있다. 지역 미선택 시 임의로 부산/사하구를 채우지 않는다. 민감정보 이용 목적을 화면에 안내한다. 선택값 삭제는 기존 값 대신 빈 값을 암호화해 저장하므로 이후 원문으로 되돌아가지 않는다.

검증: 관련 서버 테스트 13개 통과(소유자 분리, 이전 보존, 삭제, 실패 후 재시도, 키 분실·변조 차단, 입력 검사). 마이 화면 테스트 5개 통과(프로필 저장·재조회·해제 포함). 가입/캘린더 포함 기존 화면 테스트 16개도 통과했다. 실제 계정 생성·탈퇴나 이메일 발송은 수행하지 않았다.
